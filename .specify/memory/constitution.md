# Portfolio Constitution

Статус: затверджено користувачем 2026-11-04. Правила цього документа діють для проєкту.

## Core Principles

### I. Спільне прийняття основних технічних рішень

Користувач бере участь у виборі технологій, архітектури, основних залежностей,
способу редагування контенту, хостингу та публікації. Асистент перед реалізацією
пояснює варіанти, рекомендує рішення та описує наслідки для складності, вартості
й підтримки. Вибір фіксується після підтвердження користувачем.
Дрібні деталі реалізації асистент обирає в межах погодженого завдання.
Новий технічний напрям або розширення обсягу роботи потребує окремого погодження.

### II. Підтвердження змін

Асистент може самостійно читати й аналізувати файли з кодом. Перед аналізом коротко
повідомляє, що перевіряє і для чого, щоб користувач розумів контекст.
Перед створенням, редагуванням або видаленням файлів асистент ставить питання
з конкретною пропозицією: простими словами пояснює операцію, яку функцію створює
або змінює та очікуваний результат. Код не замінює цього пояснення.
Після погодження задачі повторний дозвіл на ті самі дії не потрібен.
Обговорення саме по собі не є дозволом на зміни.
Дрібні помилки, зокрема знайдені поза погодженою задачею, асистент виправляє самостійно
й коротко зазначає виправлення у підсумку. Цей виняток не дозволяє змінювати погоджені
вимоги, дизайн чи основні технічні рішення; якщо вплив виправлення неясний,
асистент спочатку пропонує його користувачу.
Дозвіл на редагування не означає дозволу на commit, push, merge або публікацію.
Кожна з цих дій потребує окремого явного дозволу користувача.
Зміни користувача потрібно зберігати.

### III. Відновлюваність та ізоляція завдань

Кожне погоджене завдання зі змінами виконується в окремій робочій гілці від відомої
базової версії. Прямі зміни в main заборонені. Робота з GitHub ведеться через робочі
гілки, логічні коміти, перевірку змін і pull request перед інтеграцією.
Асистент самостійно перевіряє стан репозиторію, базовий commit і можливість відновлення
перед редагуванням; користувач не зобов'язаний виконувати чи підтверджувати ці перевірки.
Якщо точку відновлення неможливо перевірити, редагування відкладається до її створення.
Сам відкат виконується лише після дозволу користувача й пояснення обсягу та наслідків.
Гілка сама по собі не захищає незакомічені файли. Деталі наведено нижче.

### IV. Реалізація за дизайном користувача

Дизайн користувача у Figma є безумовним джерелом візуальних рішень для реалізації.
Користувач надає дизайн та адаптивні макети через MCP. Асистент перевіряє доступ
до потрібних фреймів, компонентів і ресурсів та фіксує, на які макети спирається.
Асистент точно відтворює наданий дизайн і не змінює його з власної ініціативи,
зокрема з міркувань зручності користування. Рішення про зміну дизайну приймає користувач.
Якщо у Figma немає потрібного стану чи деталі, асистент пояснює, чого бракує,
і пропонує варіант для погодження перед реалізацією.
Користувач надає макети для комп'ютера та мобільної версії. Адаптацію для планшетів
і проміжних ширин асистент опрацьовує самостійно зі збереженням наданого дизайну.
Це делегування не дозволяє змінювати сам дизайн або спрощувати його ефекти без погодження.
Розбіжності між макетами й письмовими вимогами виносяться на уточнення;
асистент не змінює дизайн самостійно для їх усунення.

### V. Зрозумілий процес і актуальна документація

Спілкування й документація ведуться українською. Команди, технічні ідентифікатори
та назви інструментів зберігають оригінальні назви.
Мова першої версії сайту — англійська. Українська версія запланована на перспективу;
її додавання не входить автоматично до обсягу першої версії. Цю домовленість потрібно
перенести до специфікації сайту під час етапу specify.
Асистент коротко й простими словами пояснює мету дій, а нові технічні поняття
пояснює при першій появі з урахуванням того, що користувач вивчає середовище розробки.
Після погодження рішення асистент самостійно фіксує його у відповідному документі
без повторного запиту дозволу на цей запис. Погоджені рішення, пропозиції асистента
та відкриті питання позначаються окремо; пропозиції не подаються як затверджені вимоги.
Тимчасовий стан верстки, експерименти й поточні задачі фіксуються в плані роботи
або документах задач, а не серед сталих принципів constitution.

## Правила Git і відновлення

### Базова гілка та підготовка

- main містить погоджену інтегровану версію. Для кожної задачі створюється робоча гілка.
- Перед роботою перевіряються поточна гілка, git status, відмінності файлів і базовий commit.
- Сторонні зміни не включаються у власну задачу й не перезаписуються.
- Створення робочої гілки входить у погоджене завдання. Її назва та базовий commit
  повідомляються користувачу. Перехід між гілками не повинен переносити чи втрачати
  незавершені зміни іншої задачі.
- Якщо Git недоступний або стан репозиторію неможливо перевірити, асистент спочатку
  повідомляє про обмеження та відновлює можливість перевірки.

### Назви гілок

Звичайні задачі: type/short-description. Використовуються малі латинські літери,
цифри та дефіси без пробілів. Назва описує одну конкретну задачу.

| Префікс | Призначення | Приклад |
| --- | --- | --- |
| docs/ | Документація | docs/project-constitution |
| feat/ | Нова функціональність | feat/project-gallery |
| fix/ | Виправлення помилки | fix/mobile-navigation |
| style/ | Візуальні зміни | style/contact-spacing |
| refactor/ | Зміна структури коду | refactor/project-cards |
| chore/ | Інструменти й налаштування | chore/development-setup |
| experiment/ | Дослідження можливостей | experiment/figma-mcp |

Якщо Spec Kit генерує гілку специфікації у форматі NNN-short-name, використовується
цей формат, наприклад 001-portfolio-home. Номер пов'язує гілку з каталогом
specs/001-portfolio-home. Формати довільно не змішуються, щоб не порушити роботу
штатних скриптів Spec Kit.

### Commit, push і merge

- Перед commit асистент надає перелік своїх змін, результати перевірок і текст повідомлення.
  Commit виконується після явного підтвердження.
- Один commit містить одну логічну зміну та лише файли погодженої задачі.
  Формат повідомлення: type: short description, наприклад
  docs: establish project constitution.
- Push окремо погоджується із зазначенням віддаленого репозиторію та гілки.
  Локальна гілка стає доступною на GitHub лише після push.
- Merge виконується після перегляду результату, відповідних перевірок і підтвердження
  користувачем цільової гілки. Перед merge фіксується попередній commit цільової гілки.
- Для перегляду на GitHub використовується pull request після погодженого push.
- Force push, переписування спільної історії та видалення гілок потребують окремого
  прямого дозволу. Завершена гілка зберігається до погодження її видалення.

### Точки відновлення та відкат

- Для чистого робочого дерева точкою відновлення є перевірений базовий commit.
- Якщо є незакомічені чи нові файли, асистент самостійно перевіряє їх збереженість
  і створює резервну копію перед редагуванням. Інший спосіб за потреби погоджується:
  checkpoint commit, резервна копія або інший явно описаний спосіб.
  Checkpoint commit також потребує дозволу на commit. Stash автоматично не створюється.
- У підсумку задачі або її робочому документі фіксуються базовий commit, робоча гілка
  й спосіб відновлення. Резервні копії не додаються до репозиторію автоматично.
- Для опублікованих комітів і змін у main перевага надається git revert: він створює
  commit зі скасуванням зміни та зберігає історію.
- Для локальних незакомічених змін відновлюються лише файли або фрагменти своєї задачі
  з перевіреної точки відновлення, без знищення змін користувача.
- Перед відкатом пояснюються його обсяг і вплив на пізніші зміни. Відкат виконується
  після підтвердження. Пряме прохання відкотити конкретну задачу є дозволом у її межах.
- git reset --hard, git clean та інші дії, що можуть знищити незбережені зміни,
  заборонені без окремого явного дозволу після пояснення наслідків.
- Готовність до відкату означає перевірену точку відновлення й описаний спосіб скасування.
  Зовнішні дані та побічні ефекти Git не відновлює: для них спосіб відновлення
  визначається до виконання відповідної дії.

## Послідовність роботи та перевірки

1. Обговорити мету задачі, очікуваний результат і відкриті питання.
2. Сформувати вимоги й уточнити невизначеності разом із користувачем.
3. Підготувати технічний план і послідовні задачі. До написання коду переходити
   лише після погодження користувачем вимог і технічного плану.
4. Асистент самостійно перевіряє Git і точку відновлення та створює робочу гілку.
5. Виконати погоджені зміни. Нові основні рішення винести на обговорення.
6. Асистент самостійно перевіряє результат відповідно до зміни: документацію —
   на узгодженість, код — на потрібну поведінку, інтерфейс — на відповідність Figma
   та адаптивність. Результати перевірок коротко повідомляються користувачу;
   невиконані перевірки та їх причини зазначаються явно.
7. Після кожної задачі надати короткий підсумок: що зроблено, що перевірено,
   які питання залишилися. Також зазначити робочу гілку, базовий commit
   і спосіб відновлення в підсумку або робочому документі задачі.
8. Commit, push, merge та публікацію виконувати лише після окремого явного дозволу
   користувача на відповідну дію.

Spec Kit застосовується покроково: constitution → specify → clarify за потреби →
plan → tasks → analyze за потреби → implement. Наступний етап не означає автоматичного
дозволу на реалізацію, commit чи публікацію. Експерименти із середовищем оформлюються
як окремі погоджені задачі й не стають вимогами до сайту без рішення користувача.

## Governance

Constitution визначає сталі правила співпраці. Специфікації, плани, задачі та результати
перевіряються на відповідність цим правилам.
Зміна сталого правила починається з пояснення запропонованої поправки та її наслідків.
Асистент змінює правило лише після погодження користувачем і явно фіксує поправку.
Якщо нова задача суперечить чинному правилу, асистент повідомляє про суперечність
і уточнює, чи користувач погоджує виняток лише для цієї задачі, чи постійну зміну правила.
Виняток не переноситься автоматично на інші задачі. Постійна зміна записується
до Constitution; виняток — у документацію відповідної задачі.
Після завершення розгляду розділів асистент надає стислий перелік усіх правил
для остаточного затвердження користувачем. До цього документ має статус редакції
для перегляду. Після затвердження встановлюється дата ратифікації та починається
етап specify — формування вимог до сайту. Затвердження Constitution не є дозволом
на commit, push, merge, реалізацію сайту чи публікацію.
Версії ведуться за SemVer: MAJOR — несумісна зміна чи скасування принципу;
MINOR — новий принцип або суттєве доповнення; PATCH — уточнення без зміни змісту.
Версія 0.5.0 позначає редакцію для остаточного перегляду з уточненими принципами II–V,
послідовністю роботи й перевірок та Governance.
Дата ратифікації встановлюється
після затвердження першої редакції, а не за датою створення чернетки.
